# ext3 토큰이 어느 렌더 경로에서 디코드되는가

작성: 2026-07-27 · 상태: **정적으로 해결** (런타임 재확인은 권장, 필수는 아님)

무장·기체 풀네임(name75 `75C000–75E800`)을 한글화하려면 4바이트 ext3 토큰
(`E5 18 xx yy`)이 그 레코드를 그리는 코드에서 디코드돼야 한다.

## 결론

**모든 사전 토큰 확장이 훅이 걸린 코드를 지난다.** 대사·aux/UI·name75 구분 없이.
따라서 스톡 `F0–FE` 토큰이 동작하는 곳에서는 ext3 토큰도 인식된다.

근거는 세 단계 전수 검색이다.

### 1. 사전 포인터 테이블을 읽는 코드는 ROM 전체에 **하나**다

`DICT_PTR_START`(`5F:7BCC`)를 LE16 즉치로 참조하는 위치를 뱅크 `00`–`7F` 전수 검색해
32건이 나왔지만, **코드 뱅크에서 실제 명령 오퍼랜드인 것은 `7A:0703` 하나**다.
나머지는 데이터 뱅크의 우연한 바이트열이다.

`7A:06E6`부터의 스톡 바이트:

```
9a b2 de 00 80   call far 8000:DEB2      ; 현재 ROM 뱅크 저장
50               push ax
b0 df            mov al,0DFh             ; 0x5F | 0x80  → 사전 뱅크
9a b5 de 00 80   call far 8000:DEB5      ; 뱅크 매핑
bb 00 30         mov bx,3000h
8e c3            mov es,bx
d1 e6            shl si,1                ; 인덱스 × 2
81 ee 00 e0      sub si,0E000h
26 8b 84 cc 7b   mov ax,es:[si+7BCCh]    ; ← 사전 포인터 테이블 읽기
```

이 블록은 leaf `7A:06CE`(`55 8b ec 83 ec 08` 프롤로그) 안에 있고, ext3 패치가
`LEAF = 0x7A06CE`로 **감싸는 바로 그 루틴**이다.

`mov al,DF`로 뱅크 `5F`를 매핑하는 다른 코드(`74:EFA9` · `77:A7F8` · `7B:5FAD`)도
있지만 전부 `7BCC`를 읽지 않는다. 뱅크 `5F`에는 사전 외 데이터도 있고 그것을 읽는
범용 코드다 — 사전 디코더가 아니다.

### 2. 그 leaf를 호출하는 곳은 **둘**이고, 둘 다 훅이 걸려 있다

뱅크 `7A` 안의 `E8`(near call) / `E9`(near jmp) 전수 검색:

| 호출자 | 정체 |
|---|---|
| `7A:0740` | **SITE1** (`0x7A0736`, stream worker) 의 호출 지점 |
| `7A:0818` | **SITE2** (`0x7A080D`, parser B) 의 호출 지점 |

`patch_3byte_dict_token.py`가 설치하는 훅이 정확히 이 셋이다 —
`SITE1 = 0x7A0736`, `SITE2_FIXED = 0x7A080D`, `LEAF = 0x7A06CE`.

(뱅크 `27`에서 `9A ... 06CE`로 보이는 far call 3건은 데이터다. 세그먼트가 `044A`로
코드 세그먼트가 아니다.)

### 3. name75/aux는 그 경로를 반드시 지난다

name75 레코드 1,206개 중 **943개가 스톡 사전 토큰을 담고 있고** 바닐라에서 정상
출력된다(실측: pure-token 221 · mixed 722). 토큰을 문구로 바꾸려면 포인터 테이블을
읽어야 하고, 그 코드는 §1에서 하나뿐임이 확인됐다. 그러므로 name75 렌더링은
`7A:06CE`를 지나며, 그 진입 경로는 §2의 훅 걸린 워커 둘뿐이다.

## 폐기된 가설 — "뱅크 7F에 두 번째 디코더가 있다"

`cmp al,F0` / `cmp al,E0` 패턴 검색에서 `7F:05CE`·`7F:0643`이 걸려 한때
"훅 없는 두 번째 사전 디코더"로 판단했다. **틀렸다.**

뱅크 `7F`은 코드지만 `7BCC` 참조가 **0건**이고 `mov al,DF`(사전 뱅크 선택)도 **0건**이다.
`7F:0580`대 실제 코드는 바이트 구간 디스패처다:

```
26 8a 07   mov al,es:[bx]
43         inc bx
3c d0      cmp al,0D0h    / jae
3c b0      cmp al,0B0h    / jb
3c a0      cmp al,0A0h    / jb
3c fd      cmp al,0FDh
3c ff      cmp al,0FFh  → mov word [si],0FFFFh ; call ; ret
3c f0      cmp al,0F0h
3c e0      cmp al,0E0h
24 0f      and al,0Fh
```

`A0`/`B0`/`D0` 경계 + 종료 마커 `FF` + 니블 마스크는 **MML형 시퀀스 드라이버**
(음악/사운드) 구조다. 사전과 무관하다. `F0`/`E0` 비교는 우연이다.

**교훈:** 바이트 패턴 일치만으로 "디코더"라고 부르지 말 것. 그 코드가 실제로
**사전 포인터 테이블을 읽는지** 확인하는 것이 판별식이다.

## 오프닝 창 예외는 디코더 문제가 아니다

`PATCH_PROGRESS.md`에 "오프닝 창(`0x6040A5–0x604570`)은 ext3 훅을 경유하지 않는다.
4바이트 `E5 18` 토큰을 쓰면 디코드되지 않고 **패딩이 옵코드로 읽힌다**"가 있다.

§1–2에 따르면 별도 디코더는 없다. 같은 문서의 남은 작업 10번이 실제 원인을 적어 뒤었다 —
그 레코드들은 **`room`이 0**이어서 4바이트 토큰이 들어갈 자리가 없다. 억지로 쓰면
레코드가 넘쳐 뒤따르는 패딩이 이벤트 옵코드로 걸린다. 즉 **용량 문제**이고
디코드 경로 문제가 아니다. (같은 부류: 적용기의 `too_short` 1,861건.)

## 왜 2바이트 토큰으로는 못 하는가

이 세션 실측. 원본 + 작업 ROM **합집합** 기준 소비자 스캔:

| 항목 | 값 |
|---|---:|
| 2바이트 토큰 인덱스 공간 (`0x000–0xFFF`) | 4,096 |
| 소비자 0인 인덱스 | **7** |
| 그중 스톡(`<3831`) | 2 |
| name75 **전용** 소비자 인덱스 | **0** |

스톡 사전 3,831 + bank10 확장 265 = 4,096으로 주소공간이 꽉 찼다.
"레코드당 2바이트 토큰 하나"는 1,206개 레코드에 대해 **불가능**하다.
여유가 있는 것은 ext3뿐 — 16뱅크 × 4,096 = 65,536 중 3,382 사용.

## name75 적용 시 지켜야 할 것

1. **크기 보존.** 원본 페이로드가 4바이트 미만인 레코드는 ext3 토큰이 안 들어간다.
   `too_short`로 **거부**할 것. 레코드를 늘리면 순차 스캔이 어긋난다.
2. 남는 바이트는 `0x00`으로 채운다. 오프닝 사고처럼 패딩이 옵코드로 읽히는 대역이
   아닌지(`event_record_heuristics`) 확인.
3. 적용 후 `verify_nondialogue_text` **check(iii) 길이·종료자**를 반드시 재확인.
   name75는 그 게이트의 스캔 범위 안이다.
4. `tools/apply_weapon_table.py`의 `encode_token_body()` / `longest_fragment_encode()`는
   **선언만 되고 호출되지 않는 죽은 코드**다. 문서화된 2·3단계(크기보존 in-place
   레코드 rewrite)는 구현된 적이 없다. 새로 쓸 때 이 두 함수를 출발점으로 쓸 수 있다.
5. 대량 적용 전 **소수 레코드 탐침 + 인게임 확인**을 권장한다. 정적 근거는 확보됐지만
   유닛 화면 실물 확인은 아직 없다.

### 인게임 확인의 장애물

인터미션·유닛 화면에 **자동으로 도달할 수 없다.** 초기 메뉴가 `A`에만 반응하고
방향키가 전부 무반응인 것이 측정돼 있다(`run_bizhawk_input_probe.py` 대조 실험 포함).
수동 세이브스테이트로 우회한 기록이 있다:

```
BizHawk-2.11.1-win-x64/WonderSwan/State/monoeye ko expanded.Cygne/Mednafen.QuickSave1.State
```

**함정:** 스테이트는 VRAM까지 복원하므로 로드 직후 화면은 원본 타일이다.
화면을 벗어났다 돌아와야(`--seq "A;w180;B;w300"`) 게임이 타일을 재업로드한다.
모르면 "패치가 안 먹었다"고 오판한다.
